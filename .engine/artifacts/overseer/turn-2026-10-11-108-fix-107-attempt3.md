What the second BLOCK showed: attempt 2 decided by the lockfile's text, and a lockfile that names the tool is not a lockfile whose runner starts it — ruff locked in an extra or a non-default group is in uv.lock, and `uv run ruff` still starts the ruff on PATH.

The fix now (.claude/hooks/gate.py): the gate decides by what the runner would really start. `tool_prefix(root, tool)` returns the lockfile runner for a tool only when (a) the lockfile has a package of that name (`lock_names`, a cheap filter: a project that never locked the tool is not asked) and (b) `runner_has`: `<runner> run python -c "…shutil.which(tool)…"` in the project answers a path, and that path is not the file plain PATH gives for the tool (compared by realpath). No answer, an error, a timeout (60 s) or the same file as on PATH means the runner would only pass the call through — then check_tool and edit_ruff fall through to what was already there: the project's virtual environment (.venv/, venv/, VIRTUAL_ENV), then the engine's pinned lookup (PATH of exactly that version, else `uvx tool@version`, else the `tools/version` block; at edit time nothing is fetched and another version neither formats nor lints). `tool_prefix(root)` without a tool — the pytest prefix in check_steps — is unchanged.

The price, and what is not claimed:
- one more runner call per tool per check for a project whose lockfile names the tool — at every edit for ruff (`uv run python -c …`), beside the `uv run ruff` calls such a project already had; not measured;
- the question goes through `uv run` / `poetry run`, which may create or sync the project's environment — as `uv run ruff` itself already did there;
- a tool that IS the project's but is reached by the runner at the very path PATH also gives (a project environment that is itself first on PATH and is not .venv/ venv/ VIRTUAL_ENV) is read as "passed through" and gets the engine's pinned version; no such layout was tried;
- real poetry was not run here (it is not installed): poetry is covered by the stand-in only.
