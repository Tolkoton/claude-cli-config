  Runner задач із присутністю власника не бере, тож закрити її звітом у `done/` — наступна сесія з вами

## Що змінилось для власника
- **Push тепер вирішує hook `park-ask-gated.py`, за середовищем** (рядок `Bash(git push…)` у
  `permissions.ask` уже не потрібен):
  - **хмарна сесія** з `CLOUD_COMMIT_POLICY="session-branch"`: push своєї гілки `claude/…` в `origin`
    іде без запитання; будь-який інший push — відмова, і в тексті відмови сказано, що саме не так
    («the remote upstream is not origin», «the refspec … does not send the checked-out branch …»);
  - **локальна сесія з вами** — запит на підтвердження, як і раніше; тепер його показує hook
    (документація Claude Code: «ask» від hook-а показує запит і в режимі `auto`);
  - **runner** (сесія без нагляду) — відмова, як і раніше: гілку надсилає сам runner. Нове: відмова й
    тоді, коли push стоїть не на початку команди. Раніше `cd . && git push …` без нагляду проходив повз
    hook (його шаблон дивився лише на початок команди);
  - push усередині `bash -c`, `sh -c`, `eval` оцінюється так само, як прямий; forced push, видалення
    гілки, push у main чи stable — відмова скрізь (`block-dangerous.sh`, поведінка без змін).
- **Ця частина діє вже зараз, ще до «так».** Але поки в `.claude/settings.json` стоїть ask rule для
  push, хмарна сесія все одно питає підтвердження: hook не може скасувати ask rule.
- **Пропозиція `docs/tasks/settings.json`** змінює рівно два списки: з `permissions.ask` прибирає
  `Bash(git push:*)` і `Bash(git push)`, у `permissions.allow` додає `WebFetch` і `WebSearch`.
  Решта файла та сама (diff — 6 рядків).
- **Перед «так» варто знати:**
  - `.claude/settings.json` належить двигуну і після наступного release потрапить у кожен встановлений
    проєкт. Отже, WebFetch і WebSearch там теж будуть дозволені без запитання, а push працюватиме за
    тим самим hook-ом (у проєктах перемикач `CLOUD_COMMIT_POLICY` за замовчуванням `off`, тож у хмарі
    там push питатиме підтвердження).
  - Коментар `_comment_philosophy` у файлі каже, що WebFetch і WebSearch живуть в особистому шарі.
    Після «так» це вже неточно, але ви просили решту файла не міняти — тому лишив як є.
  - Без `python3` hook не запускається (Claude Code вважає таку помилку неблокуючою), і після «так»
    push тоді пройде без запитання. `env-check.sh` на початку кожної сесії повідомляє, якщо `python3` немає.

## Чому hook — `park-ask-gated.py`, а не `block-dangerous.sh`
1. Робота `park-ask-gated.py` — саме те, чим став push: рішення за середовищем про команду, на яку
   потрібен дозвіл людини (без нагляду — відмова, з наглядом — запит). Дзеркальний список ask теж там.
2. Push потребує трьох відповідей: allow, ask, deny. `park-ask-gated.py` уже відповідає JSON-ом
   (`permissionDecision`). `block-dangerous.sh` — hook однієї відповіді (exit 2 = відмова), і його правила
   діють «хоч би що відповіли на запит». Додати туди «ask» і «allow» означало б змінити його контракт.
3. Python читає команду точніше (лапки, `cd`, перенаправлення, `git -C`), і його легше тестувати.
4. `block-dangerous.sh` лишає собі безумовні відмови: forced push, видалення гілки, push у main чи stable.
   Його поведінку не змінено, оновлено лише коментарі й один рядок тексту відмови. Claude Code поєднує
   відповіді двох hook-ів так: deny > ask > allow, тому відмова `block-dangerous.sh` перемагає будь-яку
   відповідь `park-ask-gated.py`. Тест перевіряє саме це поєднання.

## Рішення, які я ухвалив сам
- **Hook — `park-ask-gated.py`** (чому — розділ вище).
- **Явне «allow» для дозволеного push у хмарі, але лише коли вся команда — це push** (плюс `cd`, `2>&1`,
  `>/dev/null`). У режимі `auto` правило `Bash` в `allow` вимикається, і вирішує класифікатор; явне «allow»
  гарантує, що push не зупиниться. Але «allow» схвалює всю команду, тож у довшій команді (чи з записом
  у файл) hook мовчить, і вирішують налаштування.
- **`git push` без remote і гілки у хмарі — відмова.** Куди він піде, вирішує конфігурація (upstream,
  `push.default`), якої hook не бачить. Текст відмови дає точну форму: `git push -u origin <гілка>`.
- **Опції хмарного push:** лише `-u`/`--set-upstream`, `-q`, `-v`, `--progress`/`--no-progress`,
  `-n`/`--dry-run`, `--porcelain`. Будь-яка інша (`--tags`, `-o`, `--no-verify`…) — відмова. Відмова й тоді,
  коли перед `git` стоїть присвоєння, є опції самого git, крім `-C`, або `GIT_*=` будь-де в команді:
  усе це може перенаправити push.
- **Хмара з перемикачем `off`** — запит на підтвердження, як було.
- **Без нагляду має перевагу над хмарою:** хмарна сесія з файлом режиму `unattended` — відмова.
- **«Без нагляду» — ще й `CLAUDE_UNATTENDED_SESSION=1`**, для всіх ask-команд (так уже читають
  `board.py`, `goals.py`, `hotfix.py`; runner ставить обидва).
- **Якщо hook не зміг прочитати push** (помилка всередині), локально він питає, у хмарі й без нагляду — відмовляє.
- **`prettier` вимкнено так само, як `ruff` і `black`** (крок 0 його не називав, але причина та сама:
  він переписав файл задачі — порожні рядки після заголовків і `unattended/\*`). Файл задачі записано
  наново, точно як у вас.
- **`CLOUD_COMMIT_POLICY` у кроці 0 перевірено в `.claude/project.env`.** У середовищі цієї змінної немає,
  і двигун її звідти не читає (`block-dangerous.sh`, `commit_checkpoint.sh`, тепер і `park-ask-gated.py`
  читають рядок у `project.env`, а там `session-branch`).

  до того порівняння з `results-task-738-086.json` показує ці 9 навмисних відмінностей.
- **Неточний `_comment_philosophy`** після «так» — окремим рядком у майбутній пропозиції, якщо захочете.
- **Хибні відмови у хмарі:** команда, що лише згадує push у тексті, який може виконатись (heredoc для

  відмова. Це той самий обережний вибір, що й у `block-dangerous.sh`; підказка в тексті відмови.
- **Не видно** (як і для небезпечних форм): push зі скрипта, який команда запускає; remote, чий URL змінила
  попередня команда; alias; `cd` у subshell hook вважає тривалим.
