# 752 — overseer_stop: останній запит на audit вибирається не за часом зміни файла — звіт

## Що змінилось для власника
- **Який запит на audit «останній», тепер читається із самих запитів, а не з часу зміни файла.** Функція
  `last_request` у `.claude/hooks/overseer_verdict.py` (рядок 316) порівнює запити так: спершу секунда в id
  (`YYYYmmddTHHMMSSZ`), далі поле `created_ns` у `request.json`, далі весь id. Час зміни файла (mtime) не читає
  жоден із двох hook-ів.
- **Stop hook бере базу для сигналу «код змінився в дереві» звідти** (`.claude/hooks/overseer_stop.py`, рядок 621).
  Два запити, записані за одну мить, або старий файл, якого хтось торкнувся пізніше, більше не роблять вибір
  випадковим — саме через це падала сцена 7b у задачі 097.
- **Кожен новий запит несе мить свого запису:** `make_request` пише `created_ns` (рядок 437). Формат id не змінився.
- **Задача чекала вас не через код.** Перший audit не знайшов жодної невдалої перевірки, але PASS не приймався, поки
  була відкрита gate escalation задачі 902. Ви її закрили й відповіли «закрито»; новий overseer перевірив роботу
  наново — PASS (request `20261012T230250Z-7a8697`). Код у цій сесії не змінювався.
- **Задача ще не в `done/` — вона знову чекає вас, і знову не через код.** Перевірка закриття
  (`mode.py check-close`) не визнає цей PASS: поки задача стояла в `blocked/`, два з трьох її файлів змінив commit
  іншої задачі (`c61466c`, board 757), а перевірка вимагає, щоб PASS бачив код точно таким, як у commit-і задачі.
  Новий audit цього не виправить. Питання 2 в задачі; виправлення перевірки — `tasks/todo/1730-…`.
- **Чого це ще не ловить:** жоден тест не перевіряє запити без поля `created_ns` — тобто всі, записані до цієї
  задачі. Код для них правильний (поле рахується як 0, вирішує id; обидва overseer-и перевірили руками), бракує
  лише тесту — це задача `tasks/todo/1726-open-item-test-gap-with-two-requests-on-disk-whose.md`.

  - Stop hook знову сам вибирає за mtime (як до задачі) — `FAIL (4)`;

- overseer сам відтворив зелений прогін і три мутації (у нього 4, 3 і 2 червоні перевірки).

**Числа червоних перевірок плавають між прогонами** — це треба знати, читаючи їх. У першій сесії було 3 / 4 / 2,
у цій 4 / 3 / 1, в overseer-а 4 / 3 / 2 (і третя червона в мутації з mtime — інша). Причину я експериментом не
встановлював; overseer підтвердив своїм прогоном, що частину перевірок у мутаціях вирішує порядок, у якому `glob`
повертає файли, і випадковий hash в id. За його ж висновком, у кожній мутації принаймні одна перевірка червона
завжди («старий запит, змінений пізніше» і «id навпаки» — для будь-якого вибору за mtime; `…-zzzzzz` — для ключа без
`created_ns`), тож випадок змінює число, а не вердикт suite. Кожну мутацію я запускав один раз.

Не перевірено: поведінку на запитах без `created_ns` тестом (задача 1726) і крок годинника назад на секунду чи
більше — тоді першою вирішує секунда в id, і порядок буде хибний; вибір за mtime цього теж не витримував.

## Рішення, які я ухвалив сам
- **Самого id замало, тому додав `created_ns`:** час в id має точність до секунди, далі йде hash, тож два запити
  однієї секунди впорядковував би випадок. Формат id не чіпав.
- **Запит без поля рахується як 0:** у межах однієї секунди для старих запитів вирішує id.
- **Зіпсований `request.json` останнього запиту читається як порожній:** сигнал іде запасним шляхом (файли, яких не
  бачив жоден прийнятий PASS), а не мовчки каже «нічого не змінилось».
- **Unit заявив руками, а не через Stop hook:** код після першого request не мінявся, тож hook audit-у не попросив би.
  Turn file `.engine/artifacts/overseer/turn-2026-10-12-board-752-close.md` і `overseer_verdict.py request` — шлях зі
  skill `overseer`, той самий, яким закрито 740 і 751.
- **Повний набір тестів запустив ще раз:** після першої сесії гілка отримала commit-и інших задач (серед них
  `c61466c`, що торкнувся `overseer_verdict.py`).
- **Перевірку закриття не міняв і в `done/` задачу не лишив:** правило, що PASS має бачити саме код commit-а, ви
  встановили відповіддю в задачі 754; послабити його заради власної задачі — не рішення агента. Відкрив 1730 і
  повернув задачу в `blocked/` з питанням.
- **Задачу 1726 не закривав сам** — у `doing/` одночасно лише одна задача.
