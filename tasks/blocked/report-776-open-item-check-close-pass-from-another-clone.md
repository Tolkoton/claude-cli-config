## Питання 1. Commit задачі, чий код потім змінив commit не цієї задачі
Сьогодні файл commit-у покрито, якщо PASS задачі бачив саме цей вміст або файл пізніше змінив покритий commit **цієї
ж** задачі. Commit власника чи іншої задачі, зроблений між двома перебуваннями задачі в `doing/`, у цю схему не входить.

- **(а) Раджу: рахувати ще й кінцевий стан.** Файл commit-у покрито також тоді, коли PASS цієї задачі бачив його з тим
  вмістом, який він має в останньому commit-і задачі. Сенс той самий, що в задачі 754: у гілці лишилось лише перевірене.
  - Я порахував це правило на задачі 732, не змінюючи коду: непокритих commit-ів не лишається. Без жодного PASS
    непокриті обидва commit-и з кодом (`7f9c831` і `969ec8c`) — негативний випадок тримається.
  - Ціна: commit власника окремого PASS не потребує; досить, що пізніший PASS задачі бачив файл після нього.
  - Повернути назад — прибрати одну умову в `unaudited`.
- **(б) Суворіше: чужий commit, що змінив файли задачі, поки вона чекала, зарахувати до задачі.** Тоді він сам має
  мати PASS. Мінус: поки задача лежить у `blocked/`, runner робить інші задачі, і їхні commit-и в тих самих файлах
  теж потрапили б сюди, а їхній PASS записано на іншу задачу. Потрібна ще одна таблиця «чий це commit».
- **(в) Нічого не змінювати.** Такі задачі закриваєте ви вручну, як 732. За три дні це сталося один раз.

Тести для (а), як просить задача:
1. Задача з двома commit-ами, другий змінює ті самі файли й має PASS — проходить (це вже тримають тести задачі 754).
2. Commit задачі, далі commit не цієї задачі в тому самому файлі, далі PASS задачі на кінцевий стан — проходить.
3. Те саме без пізнішого PASS — не проходить, названо commit задачі.
4. Commit без жодного PASS на його код і без пізнішого PASS на ті самі файли — не проходить.

## Питання 2. Звідки брати PASS, записаний в іншому клоні
- **(а) Раджу: нізвідки; у новому клоні просити новий audit.** Стан лишається в `.claude/state/`. Рядок
  «PASS … у журналі вердиктів немає» отримує підказку: якщо audit пройшов в іншому клоні — `python3
  .claude/hooks/overseer_verdict.py request <файл ходу>`. З (а) з питання 1 такий audit кінцевого стану закриває
  задачу. Ціна: одна додаткова сесія overseer-а на задачу, яку перевіряли в одному клоні, а закривають в іншому.
- **(б) Писати PASS з відбитком дерева в git.** `overseer_verdict.py` дописує рядок (запит, задача, HEAD, вміст файлів)
  у файл сесії під `.engine/journal/`, `check-close` читає і його. Нового audit-у не треба. Мінуси: новий вид
  файла-стану в git, який hooks читають як рішення; агент може дописати туди рядок звичайним редагуванням; коду —
  кілька десятків рядків у двох hooks плюс `journal.py`.
- **(в) Читати `ledger.md`.** Не раджу: у записі є лише номер запиту, без відбитка. `check-close` знав би, що PASS
  був, але не знав би, який код він бачив, і правило «саме той PASS» зникло б.

## Побічна знахідка

Для 732 такі всі чотири знайдені PASS: її власний `…-7e3795` (запит зроблено вручну, коли задача вже лежала в
`done/`), один раніший (`…-850689`) і два audit-и пізніших робіт (`…-103600`, `…-0990e4`).
Це так і сьогодні; правило (а) з питання 1 цього не змінює, але робить помітнішим: пізній чужий PASS, що бачив
кінцевий вміст файла, теж покриває. Окремого питання не ставлю: звузити можна тією ж зміною (PASS без задачі
рахувати лише тоді, коли його HEAD лежить у межах commit-ів задачі) — зроблю, якщо оберете (а), і напишу про це у звіті.
