# 750 — Свіжий хмарний клон shallow: проєкт рішення

Нічого не збудовано. Платних прогонів не було.

## Коротко
Раджу варіант **Б**. SessionStart hook `env-check.sh` уже запускається на початку кожної сесії. У хмарній сесії, на shallow clone і лише в проєкті, де це ввімкнено одним ключем у `.claude/project.env` (у двигуні — так), він сам виконує `git fetch --unshallow --tags origin`. На цьому репозиторії це займає близько секунди. `settings.json` не змінюється, вашої дії в налаштуваннях середовища не треба.

## Що відомо (перевірено)
- Хмарна сесія стартує з shallow clone: 88 commit-ів, жодного tag (задача 602, 2026-10-08).
- Дві suites швидкого набору потребують історії: `tests/test_legacy_records_survive.py` — tag `v0.10.1`, `tests/test_analyst_evals.py` — commit `cebc005`. Обидві входять у `bash tests/run_all.sh --fast`, тобто в `TEST_CMD` Stop gate-а. Без історії gate блокує кожен turn, у якому змінено код.
- `git fetch -q --unshallow --tags origin` на свіжому shallow clone цього репозиторію (`git clone --depth 50`) зайняв **1,1 с**. Після нього обидві suites зелені: 9/0 і 41/0 (задача 602).
- `.claude/settings.json` уже має SessionStart hook `bash "$CLAUDE_PROJECT_DIR/.claude/hooks/env-check.sh"`. Hook-скрипт агент змінювати може, `settings.json` — ні.
- `CLAUDE_CODE_REMOTE=true` у хмарній сесії: так хмару вже розпізнають `commit_checkpoint.sh` і `block-dangerous.sh`.
- Не перевірено: чи setup script хмарного середовища виконується після клонування репозиторію. Документація середовища цього не каже.

## Варіанти
**А. Setup script хмарного середовища** (ваша дія в налаштуваннях середовища: меню середовища в заголовку сесії → Edit → Setup script).
- Плюси: у репозиторії нічого не змінюється.
- Мінуси: не перевірено, чи скрипт бачить уже склонований репозиторій. Стосується лише цього середовища: інші середовища й інші проєкти двигуна цього не отримають. З репозиторію цього не видно і тестом не перевірити.

**Б. `env-check.sh` дотягує історію сам** (рекомендую).
- Умова: `CLAUDE_CODE_REMOTE=true`, `git rev-parse --is-shallow-repository` дає `true`, а в `.claude/project.env` стоїть новий ключ `CLOUD_FULL_HISTORY="on"`. Двигун ставить його лише собі. У встановлених проєктах ключа немає, і там hook тільки пише один рядок у вже наявний блок «missing on this machine»: «shallow clone — тести, яким потрібна історія git, не пройдуть; `git fetch --unshallow --tags origin`».
- `git fetch` з обмеженням часу (`timeout 60`). Hook нічого не пише, якщо все вдалося, і пише один рядок, якщо ні. SessionStart hook не може блокувати і ніколи не падає (exit 0) — так, як `env-check.sh` працює й зараз.
- Перевірка: `tests/test_env_check.py` з PATH shim для `git`, що записує свої аргументи. Чотири випадки: хмара + shallow + ключ → fetch викликано; без ключа → лише рядок; не хмара → нічого; не shallow → нічого.
- Плюси: у репозиторії, перевіряється тестом, без вашої дії, близько секунди на старті.
- Мінуси: мережа на старті сесії. Якщо fetch не вдасться (немає мережі чи доступу), дві suites лишаться червоними — але причину буде названо в першому ж повідомленні сесії.

**В. Дві suites самі кажуть, що історії немає**, і лишаються червоними: «shallow clone: немає v0.10.1 — git fetch --unshallow --tags origin».
- Плюси: найдешевше.
- Мінуси: лише краща діагностика; gate блокує так само.

**Г. Третій стан у `run_all.sh`** — «не запущено: shallow clone», який не рахується червоним. **Не раджу.** Це прихований пропуск тестів (перевірка #4 overseer-а): gate пропускав би зміну, яку дві suites не перевірили. Той самий стан сховав би й справжню відсутність історії на сервері.

## Що будувати за Б
- `.claude/hooks/env-check.sh`: близько 12 рядків.
- `.claude/project.env` двигуна: ключ `CLOUD_FULL_HISTORY="on"` з коментарем, що він робить. Seed встановлених проєктів ключа не отримує.
- `tests/test_env_check.py`: чотири випадки вище.
- `.claude/references/hooks.md`: один рядок у описі `env-check.sh`.
