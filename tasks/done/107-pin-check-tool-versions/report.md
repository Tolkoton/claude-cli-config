# 107 — Точні версії інструментів, якими двигун перевіряє код — звіт

## Що змінилось для власника
- **Нова версія інструмента більше сама не міняє вердикт.** Версії всіх зовнішніх інструментів, від яких
  залежить вердикт перевірок двигуна, записано в одному місці: `.claude/hooks/tool_versions.py`.
  - ruff 0.17.0 (з ним код двигуна чистий);
  - mypy 2.4.0;
  - vulture 2.16;
  - pylint 4.1.2;
  - для власних вимірів двигуна (evals, набори simplifier-а): pytest 9.1.1, Hypothesis 6.168.5, coverage.py 7.16.2.

  З цими версіями тести зараз зелені: їх `uvx` давав 9 жовтня ввечері.
- **Як шукається інструмент:**
  1. на PATH саме тієї версії — береться як є, без мережі;
  2. інакше `uvx <інструмент>@<версія>`;
  3. інакше перевірка не судить мовчки: `test_engine_lint` червоніє і називає обидві версії; stop gate
     блокує хід правилом `tools/version` з поясненням; сигнал simplifier-а стає `unavailable` з причиною.
- **У встановлених проєктах** версія проєкту має перевагу, якщо він задає її сам: lockfile (`uv run` /
  `poetry run`), інструмент у його віртуальному оточенні (`VIRTUAL_ENV`, `.venv/`, `venv/`) або власна
  команда (`LINT_CMD` / `TYPECHECK_CMD` / `FORMAT_CMD`). Глобальний інструмент іншої версії — не вибір
  проєкту, і двигун його не бере.
- **Форматування після кожного правлення нічого не завантажує.** ruff іншої версії на PATH тепер не
  форматує і не лінтить (у звіті gate про це є запис `log`), а black лишився запасним лише там, де ruff
  немає зовсім. Тож хмара з її зайвим ruff 0.16.8 поводилась би як сервер навіть без кроку 0.
- Підняти версію — окрема задача: зміна одного рядка в `tool_versions.py`, а `tests/test_tool_versions.py`
  не пропустить виклику через `uvx` без версії.

## Демонстрація на хвилину
```bash
python3 .claude/hooks/tool_versions.py             # кожен інструмент, його версія і як він запуститься тут
python3 tests/test_tool_versions.py | tail -1      # PASS 19   FAIL 0
python3 tests/test_engine_lint.py | tail -3        # ruff 0.17.0 … All checks passed! / mypy 2.4.0 … Success
python3 tests/test_gate.py | grep "board 107"      # блок з поясненням, uvx з точною версією, інструмент проєкту
```
Негативні випадки (усі в тестах):
- ruff 0.16.8 на PATH, `uvx` немає → `tool_versions.py ruff` exit 1: «ruff on PATH is 0.16.8, and the
  engine checks with ruff 0.17.0 …»;
- те саме в gate → stop заблоковано: «TOOL VERSION [tools/version] ruff did not run: …», старий ruff
  нічого не судив;
- vulture 2.10, `uvx` немає → сигнал `unavailable` з причиною, жодного «чисто»;
- у коді виклик `["uvx", "ruff", …]` без версії → `test_tool_versions` червоніє з іменем файла і рядком.

## Рішення, які я ухвалив сам
- **Одне місце — Python-модуль у `.claude/hooks/`**, а не текстовий файл: він їде в кожен проєкт разом із
  hooks (`.claude/**` належить двигуну), і в ньому ж живе однакова для всіх логіка пошуку.
- **PATH першим, якщо версія точна**, потім `uvx`: без мережі там, де інструмент уже стоїть; підробні
  інструменти тестів лишаються робочими (вони тепер називають записану версію).
- **Проєктна версія = lockfile, віртуальне оточення проєкту або власна команда.** Глобальний інструмент на
  PATH іншої версії до цього не належить: сервер і хмара мають судити однаково.
- **pytest у проєкті не закріплено**: він запускає код проєкту в його оточенні; через `uvx` у нього не було б
  залежностей проєкту. Закріплено лише для власних вимірів двигуна.
- **Форматування і швидкий lint нічого не завантажують**: інакше в самому двигуні кожне правлення почало б
  переформатовувати цілі файли й на сервері (двигун не відформатований ruff-ом, див. 749).
- **black, prettier, jq не закріплено**: це formatter-и, не перевірки, і вердикт від них не залежить.
- **`uvx pip-audit` у коментарі `project.env`** — приклад команди проєкту, не двигуна; не чіпав.
- **Інструменти в `tasks/done/085-…/tools/`** — історичні скрипти виконаної задачі; не чіпав.
