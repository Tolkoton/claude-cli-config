# 031 — Після трьох BLOCK задачу паркує скрипт, а не агент: звіт

## Що змінилось для власника
- **Після третього BLOCK поспіль на одному юніті агента більше ні про що не просять.** Коли працює виконавець дошки, hook наприкінці ходу (`overseer_stop.py`) сам зупиняє сесію (`continue: false`) і лишає виконавцеві позначку з трьома вердиктами: `.claude/state/board/three-blocks-<задача>.json`.
- **Задачу в `blocked/` переносить виконавець** — тим самим шляхом, що й будь-яку застряглу (`board.py park <задача> three-blocks`): у розділі `## Чому зупинилась` стоять юніт і три вердикти наглядача (час, номер запиту, номер перевірки, причина), під ними — одне питання до власника. Незакомічена робота агента йде в git stash, команда повернення — у тому ж розділі.
- **Подія записується в `tasks/ANOMALIES.md`** і тому видна в огляді (розділ «Аномалії»). Після цього виконавець бере наступну задачу.
- **Будь-яка ваша відповідь** повертає задачу в чергу, і юніт отримує три нові спроби: старі BLOCK удруге задачу не паркують.
- **Інтерактивна сесія (без виконавця):** поведінка як раніше, але запис у `.engine/overseer/parked.md` тепер робить сам hook, а людина бачить окреме повідомлення українською з трьома причинами. Якщо в `doing/` лежить задача, перенести її в `blocked/` там, як і раніше, просять агента — поруч людина.
- Hook-и периметра не чіпав: змінено лише hook наглядача, виконавця і `board.py`.
- Набуде чинності з наступного запуску виконавця: поточний процес працює на коді, який уже завантажив.

## Демонстрація на хвилину
Підроблений claude тричі заявляє юніт готовим; кожну заяву проводять справжні hook-и наглядача, і кожна отримує BLOCK. Далі працюють лише скрипти.
```text
$ python3 tests/test_board_runner.py | sed -n '/^three BLOCKs in a row/,/^  ok   the runner.s head/p'
three BLOCKs in a row on one unit: the hook stops the session, the runner parks the task and takes the next
  ok   the hook, under the runner, stopped the session and asked nothing of the agent
  ok   the runner moved the task to blocked/ after ONE session — the fake never touched the task file
  ok   «Чому зупинилась» carries the unit and the three overseers' verdicts
  ok   …and one question to the owner, unanswered
  ok   the event is in the anomaly journal
  ok   the runner took the next task: it is done by the second call
  ok   one commit holds the move and the journal; the event is logged; the marker is gone
  ok   the ledger the audits wrote is kept in the stash the task names, and the tree is clean
  ok   the review shows it among the anomalies
  ok   after the owner's answer the task is taken again and finished: the old BLOCKs do not park it a second time
  ok   the negative case: a session without three BLOCKs is simply continued — nothing is parked
  ok   a marker left by a runner that died before parking: the next runner parks the task first, with no session for it
```
Так виглядає задача в `blocked/` після такого прогону (з тестового світу):
```text

  - BLOCK 2 (2026-10-04T11:58:36Z, запит `20261004T115835Z-3bf669`, перевірка #4): ПРИЧИНА-2: the assertion passes without the fix
  - BLOCK 3 (2026-10-04T11:58:36Z, запит `20261004T115836Z-24ca5b`, перевірка #4): ПРИЧИНА-3: the assertion passes without the fix
```

І події виконавця: одна сесія на задачу, потім паркування і наступна задача.

## Перевірки
- Нові перевірки спершу були червоні без змін у коді: з вимкненим розпізнаванням виконавця впали 3 перевірки `tests/test_overseer_fresh.py`; на старому `board.py` впала перевірка `tests/test_board.py`.
- `tests/test_overseer_fresh.py`: під виконавцем — зупинка сесії й позначка з трьома вердиктами, нічого в `parked.md`; без виконавця — запис у `parked.md` і повідомлення людині; два негативні випадки (задача є, але виконавець мертвий; виконавець є, але задачі в `doing/` немає) — позначки немає.
- `tests/test_board.py`: вердикти з позначки стають рядками в задачі; без читабельної позначки задача все одно паркується, вердиктів не вигадано.
- `tests/test_board_runner.py`: 218 перевірок, 0 червоних (12 нових і одна про посібники).
- Повний набір, один раз наприкінці: `bash tests/run_all.sh` — 59 наборів, усі зелені. Сценарії hook-ів: 148 із 148, поведінка тотожна базовій.
- **Живого прогону зі справжнім claude не було.** Те, що `continue: false` від hook-а зупиняє справжню сесію, я знаю з документації Claude Code, а не з досліду: для досліду потрібні три платні аудити, а задача їх не дозволяє. Якщо сесія все ж не зупиниться, позначка лишиться, і виконавець припаркує задачу одразу після сесії — якщо агент за цей час не закрив її сам.

## Рішення, які я ухвалив сам
- **Hook зупиняє сесію, а не просить агента закінчити хід.** Так агент після третього BLOCK не отримує жодного ходу — правило справді виконує скрипт. Ціна повернення: один рядок у `overseer_stop.py`.
- **«Працює виконавець» — це живий процес із `.claude/state/board/lock` і задача в `doing/`.** Змінна оточення чи файл режиму означають лише «ніхто не дивиться»; під супервізором виконавця немає, і позначку ніхто б не забрав.
- **Журнал наглядача (`.engine/overseer/ledger.md`) іде в stash разом з іншою незакоміченою роботою**, як при кожному паркуванні: виконавець комітить лише `tasks/`. Вердикти тому скопійовано в саму задачу, а лічильник BLOCK живе у стані hook-ів і не губиться.
- **Гілку «позначка є, а агент уже закрив задачу сам» я прибрав:** hook лишає позначку лише для задачі, що лежить у `doing/`, і одразу зупиняє сесію, тож такого стану не буває. Натомість покрито справжній випадок — виконавець помер до паркування.
- **Повідомлення людині в інтерактивній сесії — українською,** як усе, що дошка каже власникові; текст для агента лишився англійською.
- Позначку для задачі, яку виконавець бере з `todo/` заново, він стирає: після відповіді власника стара позначка недійсна.
