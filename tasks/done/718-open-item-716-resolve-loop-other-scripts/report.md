# 718 — Петля символьних посилань давала traceback у чотирьох скриптах: звіт

## Що змінилось для власника
Якщо шлях, поданий скриптові, виявляється символьним посиланням на самого себе, скрипт тепер відповідає своєю звичайною відмовою, а не падає з помилкою Python. Це стосується шести місць у чотирьох скриптах:

- `bugfix.py prove|pins --test <петля>` — «the test file … is not a file of this project»;
- `goals.py check <абсолютний шлях-петля>` — «REFUSED: …: no such file»;
- `lesson_queue.py`, підрахунок бюджету контексту — `@import`, що є петлею, і сам `CLAUDE.md`-петля рахуються як відсутній файл, підрахунок іде далі;
- `board.py start <петля>` — «… is not a task file in tasks/todo/»;
- `board.py audit-allowed --tasks-dir <петля>` — «paid audit not allowed: no task of this session is in …».

Перші чотири названо в задачі; два останні (`--tasks-dir` і сам `CLAUDE.md`) знайшов наглядач у тих самих файлах, і їх виправлено тут же. Нічого іншого в поведінці не змінилось.

Ваша вказівка виконана: збережену роботу повернуто й доведено до commit-а (`9985712`). Commit ніщо не зупиняло — ні ворота, ні hook, ні класифікатор. Чому попередні три спроби лишились без commit-а, написано нижче, у «Чому задача застрягла».

Два BLOCK перед ним стосувались не коду, а речення в записі про помилку: я двічі назвав пошук таких самих місць повним, і двічі наглядач відтворив ще місця. ## Чому задача застрягла
Три попередні спроби пішли на три заяви наглядачеві (BLOCK, BLOCK, PASS) — жодна не дійшла до commit-а, і виконавець відклав задачу за правилом «три спроби без commit-а». Код був готовий уже після першої.

У цій сесії спроба закінчувалась без commit-а ще раз із тієї самої причини, тільки з іншого боку: я чекав повного набору тестів до commit-а, а він ішов дуже повільно. На сервері два ядра, і водночас у клоні `~/engine-attended` ішло кілька повних прогонів тестів (сесія «з присутнім власником»); набір, що зазвичай триває дві хвилини, за десять хвилин пройшов 12 із 72. Перший прогін зупинила межа часу фонової команди, другий загинув разом із сесією. Тоді я закомітив виправлення одразу (докази й чотири набори вже були зелені), а повний набір запустив окремим процесом, що переживає кінець сесії; він пройшов за 27 хвилин.

## Рішення, які я ухвалив сам
- **Роботу повернув через `git stash apply 72393f1`, а не через `git cherry-pick -n` з wip-гілки, як написано у відповіді.** Вміст той самий (виконавець зберіг одне й те саме в обох місцях; різниця — лише файл задачі 719, який уже є в гілці). `cherry-pick` у правилах двигуна серед команд, які без людини в розмові не запускаються взагалі, а `stash` дозволений. Перевірив, що зміни коду й тестів після відновлення збігаються із збереженими рядок у рядок.
- **Два конфлікти під час відновлення — у `.engine/lesson-queue.md` і `.engine/overseer/ledger.md` — розв'язав, лишивши обидві сторони** в порядку за часом: записи цієї задачі й записи задач, виконаних після її зупинки. Нічого не викинуто.
- **`base_commit` у бюджеті запису про помилку пересунув із `98fc93e` на `8eecf0f`.** Робота тепер стоїть на новішому commit-і; зі старою базою і бюджет, і доказ міряли б разом із нею сто чужих файлів. Числа бюджету не змінював. Докази запустив заново проти нової бази; у розділі 6 запису лишились виводи перевіреного наглядачем прогону, а про повторний сказано в розділі 7.
- **Закомітив виправлення до повного набору тестів**, а не після: порядок «спершу все перевірити» вже чотири рази лишив задачу без commit-а. Повний набір пройшов на тому самому commit-і.
- **Два місця, які знайшов перший аудит, виправив тут; сім, які знайшов другий, — ні.** Перші два лежать у тих самих двох файлах і вклались у бюджет; решта — інші файли, один без тестів, і це окрема задача 719.
- **`goals.py` виправлено через `os.path.realpath`, не через `try`:** `try` робив `cmd_check` складнішою за дозволену межу. Що `realpath` дає той самий результат для звичайного шляху, тримає окрема перевірка.
