# 716 — Петля символьних посилань давала traceback замість відмови: звіт

## Що змінилось для власника
Якщо в репозиторії лежить символьне посилання, що вказує саме на себе, і спрощувач назве його у знахідці, перевірка тепер просто відхиляє цю одну знахідку («не файл цього репозиторію»), а не падає з помилкою Python і не губить усю відповідь агента. Друга думка для такого шляху відповідає «не надсилати». Більше нічого у поведінці не змінилось.

## Демонстрація на хвилину
```bash
python3 tests/test_simplifier.py | grep "board 716"        # 2 перевірки, обидві ok
python3 tests/test_second_opinion.py | grep "board 716"    # 4 перевірки, усі ok
```
Щоб побачити саму помилку: у `.claude/hooks/simplifier.py:133` тимчасово прибрати `, RuntimeError` і запустити ще раз — чотири перевірки про петлю впадуть із `RuntimeError("Symlink loop from …")`. Потім повернути рядок (`git checkout .claude/hooks/simplifier.py`).

## Що зроблено
- **Виправлення — один рядок:** `_project_ref` у `.claude/hooks/simplifier.py:133` ловить ще й `RuntimeError`. До Python 3.12 саме так `Path.resolve()` повідомляє про петлю посилань. Нового робочого коду — нуль рядків, бюджет складності дотримано.
- **Тести про петлю (були червоні, стали зелені):** петля як ціль і як посилання в доказах відхиляється звичайною помилкою перевірки; `may_send` для петлі повертає «ні»; знахідка з такою ціллю не дає запиту до другої моделі.
- **Тести на побічний ефект із запису 003 (були зелені від початку):** посилання, що веде за межі проєкту, не надсилається — ні коли його названо у твердженні, ні коли воно прийшло як збіг `git grep`. Що вони справді стережуть, показує мутант: якщо `may_send` судить шлях як написано, обидва падають.
- **Запис про помилку:** `.engine/bugs/004-symlink-loop-traceback.md` — відтворення, причина, доказ, урок.

Перевірено:
- `bugfix.py prove` для обох наборів: `PROVED` — тест падає на `11cfe89` і проходить на виправленому коді;
- швидкий набір — 32 набори зелені; повний `bash tests/run_all.sh`, один раз наприкінці — 70 наборів зелені;
- `ruff` і `mypy` на цьому сервері не встановлені, тож перевірки стилю й типів не запускались; `py_compile` зміненого модуля проходить.

Чого тести не тримають (зауваги наглядача, записані в розділі 7 запису):
- `git grep` у робочому дереві ніколи не читає посилання, тож збіг на посиланні в тесті підставлено штучно; справжній шлях до посилання — коли його названо у твердженні, і він покритий окремо.
- На Python 3.13 петля вже є `OSError`, і нові тести були б зелені й без виправлення. Доказ чинний для 3.12 і старіших; сервер працює на 3.12.13.

## Рішення, які я ухвалив сам
- **Сусідів не виправляв тут.** Чотири інші місця — це чотири файли й чотири окремі червоні тести; у виправлення одного рядка вони не вкладаються, тому стали задачею 718.
- **Збіг `git grep` на посиланні підставлено через обгортку `budget.git`.** Інакше цей випадок, прямо названий у задачі, перевірити неможливо: справжній `git grep` такого збігу не дає.
- **Тест ловить `RuntimeError` лише для того, щоб надрукувати його як FAIL.** Без цього один червоний випадок обривав би весь набір, і решти перевірок не було б видно.
- **З черги уроків викинув тільки очевидні дублікати.** Уроки аналітика, спрощувача й попередніх виправлень потребують окремого розгляду, а не побіжного рішення посеред виправлення помилки. Чотири з них кажуть те саме («тесту бракувало, бо всі випадки подавали вхід одним способом») і схожі на кандидата в правило — це варто вирішити вам.
