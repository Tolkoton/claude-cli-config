# 074 — Команда /bugfix: звіт

## Що змінилось для власника
- **З'явилася команда `/bugfix`** — повне виправлення однієї помилки, вісім кроків зі схваленого
  проєкту (070, розділ 3): запис помилки → відтворення → тест, що падає з правильної причини →
  причина, записана до виправлення, і пошук таких самих місць → мінімальне виправлення →
  механічний доказ → ворота «не гірше» і наглядач → урок у чергу уроків.
- **Запис помилки — `.engine/bugs/<номер-назва>.md`,** з шаблону `.claude/templates/bug-record.md`.
  Він водночас контракт і звіт: наглядач перевіряє роботу за ним (рядок про це додано у
  визначення наглядача) і сам перезапускає доказ, а не вірить вставленому виводу.
- **Три спроби відтворення — і все.** Спроба — це інший спосіб, а не та сама команда ще раз. Не
  відтворено за три — задача паркується з усім, що пробували; робочий код не змінюється зовсім.
  Четвертої спроби й виправлення навмання немає.
- **Бюджет виправлення — сигнал, а не стеля.** У записі вже стоїть готовий малий бюджет: нуль
  нових файлів, публічних імен, абстракцій і залежностей, 40 нових рядків робочого коду (тести
  не рахуються). Перевищення кличе спрощувача; не визнав виправданим і зменшити не вдається —
  це вже не помилка, а зріз через `/plan-slice`. Числа в записі агент не редагує.
- **`bugfix.py prove` — доказ програмою, за секунди.** У тимчасовій копії: код *до* виправлення
  з новим тестом мусить упасти, код *після* — пройти. Відмовляє, коли тест проходить і без
  виправлення; коли падає і з ним; коли, крім тесту, нічого не змінено; коли команда не
  запустилась або не вклалась у час (це не «тест упав»); з `--expect` — коли тест падає, але не
  з тією ознакою, що в записі. У проєкті скрипт нічого не пише.
- **Той самий скрипт у зворотний бік — `bugfix.py pins`:** тест, що фіксує нинішню поведінку,
  проходить на коді до видалення. Це перший шлях крізь захист від видалення (072); підказка
  захисту й `gate.md` тепер називають команду.
- **«Очікуване» ніде не записане — це питання до вас, а не виправлення.** Команда спершу шукає,
  де очікуване записано (документ, тест, контракт, профіль, цілі, ваші слова в задачі). Не
  знайшла і вивести з профілю чи цілей не можна — питання власникові; без вас — задача в
  `blocked/`, код не чіпається.
- Конституцію і `.claude/settings.json` не змінено. Платних прогонів і аудиту не було.

## Демонстрація на хвилину
```bash
python3 tests/test_bugfix.py     # 75 перевірок, близько 5 с; сцени задачі — перші три рядки «ok»
```
Те саме руками, у будь-якій порожній теці:
```bash
git init -q demo && cd demo
printf 'def add(a, b):\n    return a - b\n' > calc.py && git add -A && git commit -qm base
printf 'def add(a, b):\n    return a + b\n' > calc.py                       # виправлення
mkdir tests && printf 'from calc import add\nassert add(2, 2) == 4, f"add(2, 2) gave {add(2, 2)}"\n' > tests/test_calc.py
python3 <двигун>/.claude/hooks/bugfix.py prove --test tests/test_calc.py \
        --cmd "PYTHONPATH=. python3 tests/test_calc.py" --expect "add(2, 2) gave 0"
```
Відповідь: `PROVED: tests/test_calc.py fails on <commit> and passes on the working tree…` з обома
виводами. Поверніть у `calc.py` мінус — `REFUSED: there is no fix`; замініть у тесті `== 4` на
`== 5` — `REFUSED: the test still fails on the code with the fix`.

Сцени з «Готово, коли» — у `tests/test_bugfix.py`, відмови показано першими:

| Сцена | Результат |
|---|---|
| тест проходить і без виправлення | відмова |
| тест падає і з виправленням | відмова, з виводом падіння |
| справжня пара | доведено; робоче дерево не змінилося, тимчасові копії прибрано |
| крім тесту, нічого не змінено | відмова: виправлення немає |
| команда не запустилась / не вклалась у час | відмова: це не «тест упав» |
| `--expect`: тест падає з іншої причини (помилка імпорту) | відмова; з ознакою у виводі — доведено |
| виправлення вже закомічене посеред задачі | без бази — відмова; база з запису помилки або `--base` — доведено |
| файл з `.gitignore` | не потрапляє в жодну копію; новий незакомічений файл зміни — потрапляє |
| `pins` | тест падає на коді до зміни — відмова; проходить — зафіксовано, навіть коли робоче дерево функцію вже видалило |
| бюджет у записі помилки | однорядкове виправлення — в межах; 41 рядок, новий файл чи нове публічне ім'я — сигнал |

Кожну перевірку скрипта я ламав навмисно (чотирнадцять поломок: «проходить до» приймається;
«падає після» приймається; відсутнє виправлення приймається; «не запустилась» рахується падінням;
вичерпаний час рахується падінням; `--expect` ігнорується; «до» береться з робочого дерева;
ігноровані файли копіюються; `pins` приймає падіння; база із запису ігнорується; запуск у самому
проєкті; копії не прибираються; незакомічені файли не копіюються; бюджетний скрипт не бачить
запису помилки) і ще сім — у тексті команди, шаблону й визначення наглядача. Одна поломка
(вичерпаний час) спершу не ловилася — сцену переписав, тепер ловиться.

Живий прогін зі справжнім pytest (через `uvx`, у тимчасовому проєкті): перша моя команда не
ставила шлях імпорту — тест «падав» помилкою збирання, і `--expect "assert 0 == 4"` відмовив: «fails,
but not for the expected reason». З виправленою командою — `PROVED`, у виводі `assert 0 == 4`.
Тобто «правильна причина» справді перевіряється програмою.

Повний прогін `bash tests/run_all.sh`: 66 наборів із 66 зелені (на commit-і `dbb187f`, один раз, наприкінці).

## Відкладене
- **Запис помилки не є повноправним контрактом для hook-ів.** Бюджет із нього читається, а от
  запит на аудит не несе його шляху й відбитка, запечатування (`contract_fingerprint.py`) його не
  покриває, і рядок `gate-allow` у ньому нічого не дозволяє: ці місця знають лише
  `.engine/slices/`. Наглядач знаходить запис через `.engine/PROGRESS.md`. Запечатати запис не
  можна в лоб — він же й звіт, тобто змінюється під час роботи; якщо знадобиться, запечатувати
  треба лише розділи 1–4. Окрема задача, коли `/bugfix` попрацює на справжніх помилках.
- **Ніщо не змушує робити доказ.** Його вимагають команда і визначення наглядача; hook-а, який
  не пропустив би виправлення без `PROVED`, немає. Так само три спроби рахує сам агент.
- **Жорсткий режим бюджету** (межа, а не сигнал) — задача 075 (`/hotfix`).
- **Проєкти, чиї тести не йдуть у чистій копії** (потрібне встановлене середовище в теці
  проєкту): команда для `--cmd` мусить сама його створити (`uv run …`), інакше доказ неможливий, і
  запис має так і сказати. Та сама межа, що в `COVERAGE_CMD`.
- Де живе перемикач режимів і хто вмикає `/bugfix` — задача 080.

## Рішення, які я ухвалив сам
- **Дві команди в одному скрипті: `prove` і `pins`.** «Той самий скрипт у зворотний бік» —
  окрема підкоманда з власним словом у відповіді (`PINNED`), а не прапорець до `prove`: у неї
  один прогін замість двох і протилежне очікування, сплутати їх має бути важко.
- **`--cmd` обов'язковий і має запускати лише новий тест.** Типовим `TEST_CMD` проєкту доказ був
  би хибним: увесь набір падає «до» з будь-якої старої причини.
- **`--expect` — необов'язковий, але команда `/bugfix` велить його давати.** Без нього «падає з
  правильної причини» лишалося б твердженням; з ним скрипт шукає ознаку у виводі падіння.
- **«Не запустилась» (коди 126, 127) і «не вклалась у час» — не падіння тесту.** Інакше
  помилка в назві команди «доводила» б будь-що. Час на один прогін — 300 с, `--timeout` змінює.
- **Немає виправлення — окрема відмова.** Якщо від бази відрізняється лише тест, скрипт каже це
  прямо й підказує назвати базу — типовий випадок, коли виправлення вже закомічене посеред задачі.
- **База — `base_commit` із бюджетного розділу запису** (`--record`), інакше `--base`, інакше HEAD.
  Один commit і для бюджету, і для доказу.
- **«Після» — це робоче дерево: усе, що git відстежує або відстежив би.** Ігноровані файли не
  потрапляють у жодну копію, щоб обидва прогони були в однакових умовах.
- **Скрипт нічого не записує — ні в проєкт, ні в стан машини.** Доказ дешевий, тож наглядач його
  перезапускає; зберігати «довідку про доказ» означало б ще одну річ, яку можна підробити.
- **Бюджет запису помилки міряє наявний скрипт бюджету,** без нового механізму: змінено один
  вираз, що знаходить контракт. Перевірка `complexity_budget.py check` працює і при вимкненому
  `COMPLEXITY_GATE`, тому команда кличе її явно.
- **Шаблон лежить у `.claude/templates/`** поруч із шаблоном контракту зрізу: запис помилки — теж контракт.
- **Паркування без дошки — запис у `.engine/overseer/parked.md` з класом `human-input`:** щоб
  продовжити, потрібне щось від людини (журнал, вхідні дані, доступ до місця, де помилка є).
- **Знайдений сусід із тією самою причиною виправляється зі своїм тестом, що падає,** — інакше
  це було б виправлення без відтворення.
- **Коли виправлення стає зрізом, тест, що падає, лишається,** а запис отримує стан «став зрізом».
- **Окремого шаблону задачі дошки для помилки не робив:** звичайна задача з посиланням на
  `/bugfix` достатня, присутність власника не потрібна.
- `tests/test_bugfix.py` не у швидкому наборі воріт (5 с; швидкий набір уже довший за свій бюджет).
- Сигналу наглядачеві не подавав: аудит платний, а задача його не замовляла.
