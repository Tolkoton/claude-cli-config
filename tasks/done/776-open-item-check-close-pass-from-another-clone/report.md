## Питання 1. Commit задачі, чий код потім змінив commit не цієї задачі — обрано (а)
Сьогодні файл commit-у покрито, якщо PASS задачі бачив саме цей вміст або файл пізніше змінив покритий commit **цієї
ж** задачі. Commit власника чи іншої задачі, зроблений між двома перебуваннями задачі в `doing/`, у цю схему не входить.

- **(а) Обрано: рахувати ще й кінцевий стан.** Файл commit-у покрито також тоді, коли PASS цієї задачі бачив його з тим
  вмістом, який він має в останньому commit-і задачі. Сенс той самий, що в задачі 754: у гілці лишилось лише перевірене.
  - Я порахував це правило на задачі 732 окремим скриптом у пам'яті, не змінюючи коду (востаннє — 2026-10-13):
    непокритих commit-ів не лишається. Без жодного PASS непокриті обидва commit-и з кодом (`7f9c831` і `969ec8c`) —
    негативний випадок тримається.
  - Ціна: commit власника окремого PASS не потребує; досить, що пізніший PASS задачі бачив файл після нього.
  - Повернути назад — прибрати одну умову в `unaudited` (`mode.py:420`).
- **(б) Відкинуто: чужий commit, що змінив файли задачі, поки вона чекала, зарахувати до задачі.** Тоді він сам має
  мати PASS. Мінус: поки задача лежить у `blocked/`, runner робить інші задачі, і їхні commit-и в тих самих файлах
  теж потрапили б сюди, а їхній PASS записано на іншу задачу. Потрібна ще одна таблиця «чий це commit».
- **(в) Відкинуто: нічого не змінювати.** Такі задачі закривали б ви вручну, як 732.

Тести, які просить ця задача, — для задачі `1730`:
1. Задача з двома commit-ами, другий змінює ті самі файли й має PASS — проходить (це вже тримають тести задачі 754).
2. Commit задачі, далі commit не цієї задачі в тому самому файлі, далі PASS задачі на кінцевий стан — проходить.
3. Те саме без пізнішого PASS — не проходить, названо commit задачі.
4. Commit без жодного PASS на його код і без пізнішого PASS на ті самі файли — не проходить.

Задача `1730` у своєму «Що зробити» вже має випадки 2–4 (відтворення задачі 752 і два негативні) і додає ще один:
файл після PASS змінено ще раз — не покрито.

## Питання 2. Звідки брати PASS, записаний в іншому клоні — обрано (а)
- **(а) Обрано: нізвідки; у новому клоні просити новий audit.** Стан лишається в `.claude/state/`. Рядок
  «…PASS overseer-а, що бачив саме цей код, у журналі вердиктів немає» отримує підказку: якщо audit пройшов в іншому
  клоні — `python3 .claude/hooks/overseer_verdict.py request <файл ходу>`. З (а) з питання 1 такий audit кінцевого
  стану закриває задачу. Ціна: одна додаткова сесія overseer-а на задачу, яку перевіряли в одному клоні, а закривають
  в іншому. Будує задача `1748`.
- **(б) Відкинуто: писати PASS з відбитком дерева в git.** `overseer_verdict.py` дописував би рядок (запит, задача,
  HEAD, вміст файлів) у файл сесії під `.engine/journal/`, `check-close` читав би і його. Мінуси: новий вид
  файла-стану в git, який hooks читають як рішення; агент може дописати туди рядок звичайним редагуванням.
- **(в) Відкинуто: читати `ledger.md`.** У записі є лише номер запиту, без відбитка: `check-close` знав би, що PASS
  був, але не знав би, який код він бачив, і правило «саме той PASS» зникло б.
