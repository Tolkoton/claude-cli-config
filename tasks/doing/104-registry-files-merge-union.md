## Що зробити
Відповідь власника 6 у `tasks/done/083-parallel-agents-design/task.md`: «зроби файли-реєстри
безконфліктними (merge=union для tests/fast-suites.txt і подібних) окремою малою задачею до spike».
Чому: на історії половина всіх конфліктів злиття — один файл, `tests/fast-suites.txt` (розділ 1
проєкту `tasks/done/083-parallel-agents-design/report.md`).
- Скласти перелік файлів-реєстрів оглядом, а не з пам'яті: файл, у який різні задачі дописують
  незалежні рядки і де порядок рядків нічого не означає. Відправна точка — файли конфлікту, які
  друкує `python3 .engine/artifacts/083-parallel/measure.py`. Файл, який переписують або де рядки
  залежать один від одного (`AGENTS.md`, `docs/engine-limits.md`, код), у перелік не входить.
- Для кожного файла переліку — `merge=union` у `.gitattributes` (файл уже є, у ньому `eol=lf`; рядки
  `merge=union` для журналів додає задача 739, тут — ще рядки для реєстрів). Якщо для якогось файла union не годиться — назвати чому і лишити його поза
  переліком; складання зі шматків не будувати без потреби (P7).
- Перевірити кожного читача такого файла на дубль рядка, інший порядок і порожній рядок після
  злиття: для `tests/fast-suites.txt` це `tests/run_all.sh` і тести, що рахують набори. Де читач
  цього не переживає — виправити читача або не вносити файл; для `tests/fast-suites.txt`, який
  власник назвав сам, — лише виправити читача або спитати власника.
- Чи їде це у встановлені проєкти через `engine.py install` — так само, як вирішила задача 739.
- Тест на синтетичному репозиторії: дві гілки дописують різні рядки в `tests/fast-suites.txt`;
  merge проходить без конфлікту, обидва рядки на місці, `run_all.sh --fast` запускає обидва набори
  по одному разу. Дві гілки дописують той самий рядок — набір запускається один раз. Негативний
  випадок: файл поза переліком конфліктує, як і раніше.
