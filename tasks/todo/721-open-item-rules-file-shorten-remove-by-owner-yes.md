## Що зробити
Збудувати для зміни правила той самий шлях, що й для promote. Агент пропонує точний новий текст правила або його видалення питанням у blocked/ — із назвою правила, старим і новим текстом слово в слово та sha256 пропозиції, як у promote-rule. Після відповіді власника, що є рівно словом «так», зміну застосовує скрипт runner-а поза сесією, а не агент; усередині сесії та без відповіді власника скрипт відмовляє. Те саме — для чистки застарілих рядків, яку згадує self-learning-orchestrator: навичка лише готує пропозицію, окремим питанням на кожен рядок або одним питанням із повним переліком. Оновити текст відмови promote про межу контексту, щоб він вів на цей шлях. Спершу проєкт рішення. Тести з негативними випадками: інша відповідь, ніж «так»; «так» під іншим текстом; запуск у сесії; правило, якого вже немає у файлі.

## Уточнення власника (сесія perimeter, 2026-10-06) — два різні питання, не плутати
1. **Як змінюється правило, коли механізм уже збудовано: без сесії з власником.** Агент кладе питання в `blocked/`; власник відповідає «так» у файлі задачі (через гілку або inbox), як на будь-яке питання; зміну застосовує скрипт runner-а поза сесією — так само, як `promote`. Сесія з власником для зміни, скорочення чи видалення правила НЕ потрібна, і руками поза Claude Code власник цей файл не править.
2. **Як будується сам механізм: рядок «Потрібна присутність власника: так» угорі стосується лише цього будування.** Він стоїть тому, що будування може зачепити perimeter (hooks `protect-paths.sh` / `block-dangerous.sh`, список `protected-path-list.sh`, `.claude/settings.json`). Якщо проєкт рішення покаже, що perimeter не зачіпається (зміни лише в `lesson_queue.py`, `owner_action.py`, `board.py`, `board-runner.sh`), рядок можна зняти, і задачу будує runner. Якщо зачіпається — будуємо в одній із сесій perimeter.
